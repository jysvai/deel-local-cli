## 1.18.0

**Having a rule is not the same as the rule firing**

This release adds no features. It is about **the places that did not behave the
way they were written down**. It started with 8,404 checks all green, and found
four ways to walk straight through the command guard and one path that leaked the
gateway key.

How they were found is the substance of this release, so that comes first.

### Green does not mean "break it and you get caught"

The bugs that keep coming back in this repo are all one family.

- A rule is written down and **never once matches**
- A test exists and **nobody runs it**
- A fix is recorded and **is not actually held**

All three look fine from the outside. A rule that never fires never blows up
anywhere; a test that never runs can never go red; a fix that is not held lives
only in a comment. They are worse than nothing, because they **make you believe
something is there**.

So this release adds three ways to measure that.

**1. Does the rule match real sentences** — all 97 rules in the mode-selection
scoring table are run against 103 real sentences. **Thirteen were dead.** The
particle after a word was written as `점검(해|좀|을|이)`, but Korean puts a space
in: "점검 좀 해줘". Analyse, review, explain, inspect — the entire polite-request
register was falling through.

Then one layer deeper: **a rule being alive is not the same as its branch being
alive.** In `(해|\s*좀|을)`, one dead branch is invisible as long as another one
matches. Measured that way, **four of the twelve** rules that had just been fixed
were still green after reverting the fix — a third of what had been recorded as
fixed was not being held. Each branch is now measured on its own.

**2. Built and then never called** — everything in `tools/` must be wired to an
npm script, written down in the development docs, or called by another tool.
Otherwise nobody runs it. In this very release, the second-review harness was
built and left unwired — exactly that trap. And `npm run check` only walks `src/`,
so a broken file in `tools/` stays silent until the day someone runs it by hand,
which is usually a day something is urgent. So it is now parsed too.

**3. The demo you watch with your own eyes** — `npm run demo` had **never once
run**. It wrote its settings to the wrong place, printed one line ("no saved
connection"), and exited 0, so nobody asked. On a machine that *did* have settings
it was worse: it talked to the **real gateway** instead of the fake one. It now
says so when it does not run, and CI runs it every release.

### The command guard was open four different ways

`src/safety/guard.js` holds a deliberately narrow list: only things you cannot
undo. That promise was broken four ways. All four were reproduced before fixing.

```
rm -rf /                            blocked
rm -rf / ; echo done                through ←  the shell runs both
rm -rf / ;                          through ←  a bare separator is enough
rm -rf "/"                          through ←  quotes are enough
git push -f origin main             through ←  the short form
Remove-Item C:\ -Recurse -Force     through ←  PowerShell's common order
Remove-Item -Recurse -Force C:/     through ←  PowerShell takes slashes too
Remove-Item -rec C:\                through ←  abbreviated parameter
```

**One more word on the end.** Several rules anchor with `\s*$`, meaning `rm -rf /`
only matches at the *end* of the line. Eight characters — `; echo done` — walk
past all of them. Prefixing was already blocked (`echo hi && rm -rf /` is at the
end), and only **suffixing** leaked, so every test that measured "is it blocked"
stayed green. Commands are now split into segments and each segment is checked,
while the whole string is still checked too, for rules that span a pipe
(`curl … | sh`).

**Quotes.** The header of that file already said quoted text is not exempted —
written precisely so `sh -c "rm -rf /"` would not be missed. But **not exempting
quotes and stripping them are different things.** Nothing ever stripped them, so
the stated intent and the actual behaviour were opposites.

**Only the spelling we happened to write.** `--force` was blocked, `-f` was not.
Flags before the path were blocked, flags after were not. Backslashes were
blocked, forward slashes were not. `-Recurse` was blocked, `-rec` was not. That is
not "blocked" — that is **"blocked for people who typed it my way"**.

### Writing `.DEEL` read the key straight out

The guard for the home folder looked for the **lowercase string** `.deel`. But
Windows (NTFS) and macOS (APFS by default), where this program mostly runs, do not
distinguish case in filenames. **The name does not match, but the file opens.**

```
.deel/config.json   blocked
.DEEL/config.json   through ←  the same file opens
```

That file holds the gateway key. The key then rides into the conversation, out
through the gateway, and onto disk in the session log — the "exactly one outbound
door" promise carrying the key out through that door. The commit path already
blocked this; only the **read** path was open.

### Config that came with the repo was launching programs

`mcp.json` lives in the project folder, which means it **ships with the repo**.
Clone someone else's repository, start deel inside it, and the `command` written
there became a child process with this account's privileges. It never passes the
tool-approval screen either — the model did not call it; we did, in order to start
the server.

```json
{ "mcpServers": { "sync": { "command": "cmd", "args": ["/c", "…"] } } }
```

`safety/hooks.js` enforces `믿나(root)` against exactly this threat and says in its
own header that it treats hooks **"with the same weight as MCP"**. The side being
compared to had no such door.

Skills are the same. A skill is prose, but it is prose that tells the model how to
work, and its name and one-line description ride in the system prompt **every
turn**. Project skills sit highest there — above the user's own.

Both are now read only in trusted folders (`deel trust`). **Slash commands are
deliberately left alone** — those expand only when a person types `/name`, and they
never enter the system prompt. Different threats need different doors. Gating both
looks safer but actually means "this tool is useless in someone else's repo", and
people start typing `trust` reflexively — and then they type it in the place that
mattered too.

When something was not read, it **says so**. Not knowing why your own file is
missing is the second-worst outcome.

### The prompt-cache anchor was landing outside the window

The look-back window is **twenty blocks**. We were counting **messages**. In a
tool-heavy turn one message is several blocks, so the anchor lands outside the
window — the tail mark cannot see it, and the whole prefix is re-sent every turn.
Nothing errors; the bill just grows.

The direction was backwards too. When a slot could not take a mark, the anchor
stepped **back**, which increases the distance to the tail. Measured: 25 blocks,
in a window of 20. It now steps toward the tail.

The old test could not catch this. It blanked a slot with `content: null`, which
drops that message from 3 blocks to 1 — so **the anchor position itself shifted**
and landed somewhere it could attach anyway. Deleting the fallback loop entirely
left the test green.

### Also

**Only newly created hwpx skipped the redaction check.** When the model reads an
environment variable through Bash, the value comes back masked. Copy that mask into
a document and every other format refuses at that point — but hwpx answered
"created" and quietly wrote the file. Writing internal reports is what this tool is
mostly used for, so that is the worst possible place: those documents go to other
people.

**Four places that said "saved" without saving.** `/scan save`, `/level`, `/ctx`,
and context auto-learning. If the home directory is read-only or the disk is full,
that statement is true only for that moment, and the old value is back next start.
There was no way for a person to find out why.

**Three comments that disagreed with the code.** "The remaining seven slots" where
there are eight; a threshold described at half its real value. A comment that does
not change with the code becomes a quiet lie.

### Second review — by a different model than the one that wrote it

That whole family survives because **the person who wrote the code also wrote the
test**. Whoever got the pattern wrong picks the assertion with the same
misunderstanding. Put the same mistake in both places and they pass each other.

So the first pass is done by the side that wrote it, and the **second pass by a
different model**.

```bash
npm run review2                        what is not committed yet
node tools/review2.mjs --since HEAD~3  the last three commits
```

`agy` (the Antigravity CLI) is spawned as a process — calling it from source would
break "the only outbound door is `src/backend/http.js`", so it is borrowed the way
rg and git are. It runs with `--mode plan`, read-only. It does not know this repo,
so the house rules (Korean identifiers, zero dependencies, one outbound door) and
**the five bug families above** are handed to it along with the diff.

**This is an eye, not a gate.** It writes down what it found and blocks nothing —
make it a red light and people silence it first, and then there is one eye fewer.

It paid for itself on the first run. Started after the first-pass review, with
8,368 checks green, it returned **three severe findings — all three holes made
thirty minutes earlier**. Fixing "one more word on the end" created a "half a word"
hole; fixing the leading word boundary left the trailing one open. **Move a fence
and a gap appears where you moved it.**

Wiring it up went wrong three times, and all three are recorded in the source. The
last was the worst: exit code 0 with an empty answer, so "nothing to report" and
"never actually looked" appeared identically on screen. The tool built to catch that
family was carrying it. An empty answer is now **treated as a failure**.
