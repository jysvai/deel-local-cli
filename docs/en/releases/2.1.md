## 2.1.8

**Suspending deel with Ctrl+Z and resuming it with `fg` no longer makes it quit**

In a macOS or Linux terminal, suspending deel with Ctrl+Z and bringing it back with `fg` dropped you to the shell
the moment it woke, without a word. Whatever you typed next went to the shell as a command
(`bash: 가라: command not found`). Suspending while an answer streamed ended deel the moment the answer finished.
Node's readline leaves input paused on resume, and nothing resumed it.

| What | Before | After |
|---|---|---|
| Ctrl+Z → `fg` (line screen, box screen) | Quit silently on wake; the next thing typed went to the shell | Carries on. The input box is redrawn and what you were typing is still there |
| Ctrl+Z → `fg` while an answer streams | Quit when the answer finished | Receives the whole answer and takes the next message |
| Ctrl+Z → `fg` at the tool approval prompt (`실행할까요? (y/n)`) | Quit | The question is printed again. `n` still refuses |
| The shell while deel is suspended | Could inherit the bracketed-paste mode deel turned on, and a cursor the spinner hid | Both are switched off before suspending and back on after waking |
| Ctrl+Z under `ssh -t host deel`, `docker run -it` or `exec deel` | The kernel drops the suspend, but raw mode was left off: keys arrived only on Enter, and arrows and Korean erase were handled by the terminal | Raw mode comes straight back and typing goes on |

From this release the macOS and Linux gate drives deel with keystrokes in a **real terminal (pty)**. The chat
screen (Korean erase, multi-line paste, resizing, Ctrl+C while streaming, Ctrl+D), the tool approval prompt (`y`,
`ㅇ`, `n`, ESC, Ctrl+C), Ctrl+Z, and `deel setup` (Ctrl+C, the masked key) are measured on both the line screen
and the box screen, and every run checks the terminal is restored afterwards. Until now the chat-screen checks used
a fake TTY stream, so raw mode, the window-size signal and restoring the terminal were never exercised. That is how
the Ctrl+Z bug turned up.

## 2.1.7

**Tab completion for file names no longer errors in zsh, the default shell on macOS**

After 2.1.6 put macOS into the gate CI, every Mac-only code path was run on a real Mac. Finding open ports, reading
.doc, .rtf, .docx and .odt through `textutil`, clipboard images, imports that differ only in case, and `deel doctor`
all worked; the three below did not.

| What | Before | After |
|---|---|---|
| Tab on a file or folder argument in zsh (`deel run my⇥`, `deel --root my⇥`) | Printed `_deel_paths:11: bad substitution` and offered nothing. zsh is the default shell on macOS | Names with spaces (`my dir`) go in as one word. Confirmed by pressing Tab in a real zsh on a Mac and reading the words the shell passed |
| Pasting a screenshot over 12 MB (macOS, Linux) | "osascript could not be run: ENOBUFS" — it looks like the tool is broken | "The image is too big (over the 12 MB limit) — capture just the part you need" |
| A Korean profile name in decomposed form (NFD) (macOS keychain) | Each re-store left an orphaned item in the keychain | Stored in one slot. Keys already stored still load |

Opening a trusted folder by a name that differs only in case (trust `MyProj`, open `myproj`) was measured on a Mac
too: the real-location comparison from 2.1.6 already handles it, and a gate check now keeps it that way. A sibling
with a longer name (`MyProjX`) is still not trusted.

## 2.1.6

**Works properly on macOS — keychain keys, trusting folders under `/tmp`, and long output read through a pipe**

For the first time the full test suite ran on a real Mac (macOS 26, Apple silicon), and the Mac-only flaws it found
are fixed. macOS is now part of the gate CI, on node 20, 22 and 24 for every change. Nothing changes for Windows
users; on Linux the second-to-last row (pipe output) is fixed too.

| What | Before | After |
|---|---|---|
| Putting a long key into the keychain | Past about 3,000 characters, one `security` line overflowed and the tail was read as a separate command | The length is measured first; if it's too long, deel says why and doesn't store it |
| Spaces, newlines or quotes in `DEEL_KEYCHAIN_NAME` | The command line split, so the key went under the wrong name (`deel`) or failed | Rejected, with the message pointing at that variable |
| A value changed by hand in Keychain Access | Garbled text was sent as the key | "Store it again with `deel setup`" |
| A locked keychain (common when you SSH into a Mac) | `spawnSync security ETIMEDOUT` after 20 seconds | "It may be locked — `security unlock-keychain`" |
| Sessions left open after changing the key (REPL, ACP) | Kept sending the old key | Use the new key |
| Trusting a folder under `/tmp` or `/var` (on macOS both are links to `/private/…`) | The same folder arrived spelled differently, so a trusted folder wasn't recognized and its project settings were dropped. Started from the home folder, deel called its own settings "untrusted project settings", and `deel reset` counted one file twice | Compared by real location. A deleted folder can be untrusted by its link-side name too |
| A pipe whose reader is slow (`deel sbom \| slow-command`, macOS and Linux) | Output over 64 KB was cut to **0 bytes** | Exits only after everything is written (waits up to 5 seconds) |
| A broken link inside a shell command (like `/.VolumeIcon.icns` at the Mac root) | Treated as a name not on disk, so the working-scope check was skipped | Anything present counts as a path and is checked |

Most of the eleven checks that were red only on macOS failed because the tests didn't know about the Mac, so the
tests were fixed: bash 3.2 completion, Apple's `unzip` printing Korean names as `?`, and test children that exit right
after large output. Along the way we found the UTF-8 name flag in ZIP files had never actually been checked; it is
now measured directly.

Taken from the code review (Gemini), three items: untrusting a deleted folder, a settings file that is **itself** a
link, and an empty key. All three were confirmed by running them, then fixed. The keychain fixes were measured one
by one on a real Mac with a throwaway keychain — locked, overflowed, hand-edited (the real limit of one
`security -i` line is 4,096 bytes; deel's limit sits inside it at 4,000).

## 2.1.5

**Shell commands could reach outside the working folder — one `find .. -delete` emptied the parent folder. Now blocked**

In the default (auto) mode, shell commands don't ask a person; they only pass the fence (working scope and
blocked-command list). That fence only checked **paths containing a slash**. So the parent folder itself (`..`)
and placeholders whose value is known (`$PWD`, `%CD%`) were never checked. A single mistaken line from the model
could delete or read the whole parent of the working folder. This is an urgent security fix, so this release
contains only that.

| Input | Before | After |
|---|---|---|
| `find .. -delete` | Passed — the working folder's parent was wiped (measured in a throwaway folder) | Blocked as outside the working scope |
| `rd /s /q ..` · `Remove-Item -Recurse ..` · `git -C .. clean -fdx` | Passed — commands that delete in the parent went to the shell unchecked | Blocked |
| `tar czf o.tgz ..` · `ls ..` | Passed — the parent could be packed up and read (up to `~/.ssh` when the working folder sits right under home) | Blocked |
| `rm -rf $PWD/../sibling` · `rd /s /q %CD%\..` · `"$(pwd -P)/../x"` · `$pwd.ProviderPath` | Treated as a placeholder with an unknown value, so the scope check was skipped | A placeholder at the start of a word is resolved to the current folder and checked |
| `rm -rf $OLDPWD` · `cd ~-/sub && …` | Passed | The previous folder is unknown, so it counts as outside (same as `~-`); for `cd ~-/sub`, when this command has not moved anywhere first |
| `cd - && rm -rf *` | Passed | Blocked unless this command moved somewhere first; `cd src && make && cd -` still runs |
| `rd /s /q C:..` (Windows) | Passed | Blocked |
| `ri -Recurse -Force C:\` · `del -Recurse ~` (PowerShell aliases wiping a drive or home) | Passed the blocked-command list (the scope check stopped it, so nothing leaked) | The list blocks it too |

**One behavior change.** `cd - && command` used to run as "go back to the previous folder". But deel starts a
fresh shell for every command, so a `cd -` with no earlier move goes to the previous folder the shell
inherited, and deel does not know where that is (the same reason `rm -rf ~-` is blocked). A lone `cd -`, and
moving and coming back within one command, still run. Plain text with `..` as its own word (`echo ..`) is now
blocked too — a rare shape, and the model rewrites it when blocked.

Taken from the code review (Gemini), four items: `cd ~-/sub` (**below** the previous folder) · a joined `cd..`
exempting a later `..` from the check · `$pwd.ProviderPath` · `$(pwd -P)`. All four were confirmed by running
them, then fixed. Besides Windows, the real Bash tool was run with deleting commands **on macOS (macOS 26,
Apple silicon)** too — they were blocked and the parent folder stayed intact.

## 2.1.4

**Connect by logging in with a browser, no key to paste — one OpenRouter login for Claude, GPT, Grok and Kimi**

"API keys are fine, but let me follow a link, log in with my account and just use it" is something we
kept hearing. Option 3 in `deel setup` is that path. The design was shown to a different model (Gemini)
before coding and the code after, and every finding was settled by running it before anything was fixed.

| | What |
|---|---|
| **Log in with a browser** | `deel setup` → **3. Log in with a browser — OpenRouter**. A browser opens; log in and a key named `deel` is created on that account. deel receives it and locks it away exactly like a pasted key (Windows DPAPI · macOS Keychain), then connects, lets you pick a model and runs the diagnosis as usual. One key covers Claude, GPT, Grok and Kimi, billed to that account as you use it |
| **How it is received — PKCE** | deel makes a random verifier and puts only its hash in the login link. When the login side hands a code back to `localhost` on this PC, deel sends code + verifier once to trade it for the key. The verifier never travels through the browser or the callback — only in that exchange — so an intercepted code is worthless, and the callback path is freshly random each run. That one exchange is the only request deel itself makes, and it goes through the single outgoing door (`http.js`) |
| **Browser on another machine** | `deel setup --no-browser` — open the link on any device, log in, and paste the code it shows (or the whole address). An SSH session, or Linux with no display, takes this path on its own |
| **It ends** | No answer within 5 minutes and it stops and closes the callback port. Decline on the login page and it stops at once. Under seal (`--offline`) it does not go out to log in and does not open the browser |
| **OpenRouter in the list** | OpenRouter is now in the vendor list. Paste a key, or leave it empty and press Enter to log in. "I only have a key" recognizes `sk-or-` — until now `sk-` caught it first and **sent it to OpenAI** |
| **Hundreds of models, still pickable** | Only the first 40 models were shown, so anything after that could not be chosen. Past 40 you narrow by part of the name (`claude` · `grok` · `kimi`), and "Enter it yourself" at the end of the list takes any name |

deel does not borrow a Claude or Codex **subscription** login — those belong to the vendors' own tools,
and a third-party tool riding on them breaks their terms or gets cut off one day, leaving you unable to
work without knowing why. OpenRouter officially offers a login that issues a key for your own account.

### Fixed

- **On Windows, an address containing `&` did not open in the browser.** `cmd /c start` treated an
  unquoted `&` as a command separator, so only the first part opened and the rest ran as a command (the
  preview address has no `&`, which is why it went unnoticed). The address is now quoted and passed as
  is, and an address containing a `%name%` that cmd would expand even inside quotes is not passed at all
  (the address is on screen).

Taken from the design review: pick another port when someone else holds the same port on `::1`
(otherwise a browser resolving to `::1` hands the code to them) · quote cmd properly instead of going
around it with `rundll32` (corporate security policy often blocks `rundll32`) · a way out when the model
search matches nothing. Taken from the code review: cmd's `%` expansion · codes with `=` padding and
`#code=` addresses · closing the connection before the page had gone out · server errors after listening
began. Refuted: the setup ordering (the seal check is a pure function, so moving it earlier changes
nothing) · connection checks blocked after the exchange (the check opens its own address) · model lists of
40 or fewer (unchanged) · any path leaking the key to the screen (none).

## 2.1.3

**Models that write tool calls as text still get work done, `deel run` picks up where it left off, what a script changed comes back with `/undo`, and MCP attaches by URL**

A release of product features. The centre is where local models usually get stuck (tool calls written
as text, no language server, large repositories) and where deel is used outside the chat screen
(`deel run` continuation, event streaming, MCP over HTTP). What changed was shown once more to a
different model (Gemini), and every finding was settled by running it before anything was fixed.

| | What |
|---|---|
| **Models that call tools in text** | When the server does not know a model's call format, `tool_calls` comes back empty and the reply text carries `<tool_call>{…}</tool_call>`, `<function=Read>`, `[TOOL_CALLS]` and the like. The turn used to end as "answered in text only". Now calls written with **a tool name we offered** are rescued into real calls — and pass the same mode, approval and policy-floor gates as native calls. Examples inside fences and JSON sitting in the middle of an explanation are not rescued. Argument JSON that is only **mis-shaped** (single quotes, trailing commas, unquoted keys) is read leniently; truncated JSON is not. The tool-call check in `deel setup` and `deel diagnose` flags such a model with a warning |
| **`deel run` continues** | `--continue` (the latest conversation in this folder) and `--resume <name>` bring back the earlier conversation and its pins. A single run is now saved under `.deel/sessions/`, and the `--json` result carries `session`. The result lists **the files that changed** (`files`), and `--events <file>` streams events as one JSON object per line while the run is going (text chunks left out, long text clipped). If the events file cannot be opened, the run stops before any work starts |
| **What a script changed comes back with `/undo`** | Files not named on the command line — `npm run format`, `node fix.js`, `rm *.tmp` — had nothing saved. In a git repository deel now compares `git status` **before and after** the command and records the earlier content of what really changed: from HEAD if it was as committed (exactly what `git restore` would write, line-ending conversion included), from a copy taken just before the command if it was being edited. Nothing is written to `.git` |
| **Syntax is checked without a language server** | When the language server gives nothing after an edit (absent, or still warming up), deel runs only the cheap checks: `node --check`, parsing JSON, brace pairs, `py_compile`. The header says "syntax check" so it is not mistaken for a language server |
| **Outline puts the core modules first** | The folder skeleton was loaded in order of recent edits only, so in a large repository the core module nobody had touched for a while was the first to be cut. deel now counts import, require and `from`, loads **the most imported files first** (the files being edited keep the first few places), and notes in each header line how many files import it |
| **MCP attaches by URL** | `"type": "http"` with a `url` attaches to a streamable HTTP server. It leaves through the same single door as the model endpoint, and the configured address is open only while a request is in flight. Under `--offline` only servers on this machine (intranet included) attach. `${ENV}` in `headers` is expanded, and a server that dropped the session gets a fresh handshake |
| **MCP resources and prompts** | If a server offers resources they are read with `mcp__<server>__read_resource`; prompts are called with `/mcp__<server>__<name> args…` (in `deel run` too). Quote an argument that has spaces in it; the last argument takes the rest as is, line breaks included |
| **Automatic mode picks up Japanese and Chinese** | The screen speaks four languages but mode routing only knew Korean and English. 「直して」 or 「请帮我修复」 now goes to the mode that edits, and 「説明して」 or 「是什么」 goes to ask |
| **Generation speed** | `/cost` shows the generation speed (tok/s) of streamed calls, and `deel run --json` carries `genMs` and `tokPerSec`. If it could not be measured, nothing is shown |

### Fixed

- **`Verify` passed a broken `.js`.** For a `.js` file with `export` in a folder whose `package.json` has no
  `"type"`, node's module detection let `node --check` exit 0 even with an unclosed bracket (measured on
  node 24). Such files are now checked once more as a module.
- **The auth command handed an earlier profile's token to another gateway.** There was one held key and one
  approval, so when `/consult` or a Task with its own model asked for a key with its own auth command, the
  earlier profile's token came back and that command was never asked about. Keys and approvals are now held
  per command. Text shown on screen masks every held key.
- **deel did not exit after an auth command timed out.** Only the shell was killed; the login tool
  beneath it kept the pipe open. The whole tree (Windows) or process group (Unix) is now reaped and the pipes released.

Of the 66 findings from seven second-review passes, 24 were taken and fixed: text tool calls (an example inside
an unclosed fence read as a call, two calls in one tag merged into one, `01234` turned into `1234`), MCP over HTTP
(requests sent together that all met an ended session, error replies without an id, OAuth-style rejection text),
script undo (when git could not produce the earlier content it was recorded as "did not exist", so `/undo` would
have deleted the file), prompt arguments (quotes and line breaks), the result line of the events file, and the
module re-check. Two more turned up while checking: in a core.autocrlf repository `/undo` brought CRLF files back
as LF, and git was started once per changed file — 120 files took about 6.7 s (now about 0.3 s). The rest were
disproved by running them: already blocked (mcp.json in an untrusted folder, `--events` without a value, an empty
`--resume`), deliberate (rescued calls still pass the approval gates; offline follows the same rule as the network
gate), or misread (porcelain paths are relative to the repository top; `rev-parse` does print the empty line).

### Faster

- **`deel run` loaded every chat-screen command.** It imported all of `commands.js` for three slash-command
  lookup functions. The lookup rules moved to a small `src/slash.js`, and the source files read went from
  133 to 105.

### Not changed

- **DNS rebinding in WebFetch.** Same reason as in 2.1.2 — it conflicts with the single outgoing door.
- **The handshake-free MCP revision (2026-07-28).** deel uses the handshake revisions (up to 2025-11-25).
  A server that accepts only the new revision names the versions it accepts, and that is shown as is.
- **The old MCP HTTP+SSE transport.** Not accepted, and the reason is given.

## 2.1.2

**confirm asks before MCP tools, editor sessions no longer pile up, and `deel --version` no longer loads the whole program**

The three policy questions 2.1.1 set aside for a decision, plus small gaps and performance. What
changed was shown once more to a different model (Gemini), and every finding was settled by running
it before anything was fixed.

| | What |
|---|---|
| **confirm asks before MCP tools** | confirm means "ask only before what cannot be undone", yet attached MCP tools were never asked about, and `/undo` cannot reverse what an MCP server did. They are asked about now, except tools the server marks as read-only (`readOnlyHint`, and not `destructiveHint`). strict still asks before all of them |
| **Editor sessions only piled up** | An editor (ACP) opens a session per conversation, and deel lives as long as the editor does. Nothing ever let a session go, so everything opened during the day stayed in memory: the conversation, the undo history, the audit log and the folder's MCP servers. Past 16 sessions (`DEEL_ACP_MAX_SESSIONS`) the idle session used longest ago is now let go; a new message to it, or `session/load`, brings it back from its file, together with the work mode the editor chose and its "don't ask again" choices. If it was the folder's last session, its MCP servers are closed too |
| **What check rounds count** | `checkRounds` is the number of **times the check runs** (one fewer chance to fix). The docs called it the number of send-backs. Unusable values such as `0`, negatives, text or `true` silently fell back to the default; they are now reported the way capped values are, with what was used instead |
| **deel eval timeouts and comparison** | `--timeout 0` or `--timeout abc` killed deel in every task at once, so everything "timed out"; it is now a usage error (64). The order, where a task's own `timeout` in task.json beats `--timeout` (as in pytest and jest), is now in the docs and in the run header. Tasks that were there last time and are gone now get a ⚠, tasks measured for the first time are listed, and "same as last time" is scoped to the tasks actually compared |
| **Completion checks per task** | task.json takes `doneCheckRounds` and `doneCheckTimeout`. `deel run` has new `--check-rounds` and `--check-timeout` flags, and eval passes them per task |

### Faster

- **`deel --version` and `--help` loaded the whole program.** The entry point imported every command up
  front, so printing a version number read 164 files (4.4 MB). Commands now load when used, and startup
  reads 18 files (471 KB). `deel --version` went from about 440 ms to about 290 ms, and the version is
  printed before any config is read.
- **The undo history was read from the start every turn.** The chat screen counts undoable turns after
  each turn, and each time it read the whole history file (it holds full pre-edit copies and grows to
  32 MB) and parsed every line. Only the appended tail is read now; if another tab rewrote the file,
  that is noticed and counting starts over.
- **The status line recounted the system prompt every 90 ms.** Token counts are remembered per piece,
  taking one frame's count from 0.23 ms to 0.03 ms.

### Fixed

- Number fields in task.json (`timeout`, `checkTimeout`, `doneCheckRounds`, `doneCheckTimeout`) read
  `true` as 1: a one-second timeout killed the task, and `--check-rounds true` made `deel run` stop
  with a usage error. Only numbers, or text holding a number, are accepted now.
- A task measured for the first time could fail while the compared tasks matched, and the run still said
  "same as last time", hiding that failure. An `--only` run compared only the chosen tasks but read as
  if everything matched.
- Opening a let-go editor session with `session/load` lost its work mode and "don't ask again" choices.
  "Last used" was also recorded as a timestamp, so two sessions used within the same millisecond tied
  and the first-opened one was let go instead of the one used longest ago; it is now an ever-increasing
  counter.

Of sixteen points from the second review, five were taken. The rest were disproved by running them:
already blocked (a bare `--timeout`, `timeout: null`, a task.json `timeout` said to be unchecked), or
the same behaviour as before and already caught by every caller (the history file vanishing mid-read).

### Not changed

- **DNS rebinding in WebFetch.** Stopping it needs IP-pinned connections, which would break the design
  where every outgoing request passes through one door (`backend/http.js`). That design is deel's
  promise, so this is left out.
- **Explicit Gemini caching.** Implicit caching works on its own from Gemini 2.5. Explicit caching needs
  cachedContents to be created, kept alive and paid for, and requires requests without system and
  tools, while deel's tool list changes from phase to phase.
- **Caching Glob results, the language server's startup walk, or the repository check.** Measured, a
  10,000-file Glob takes about 206 ms and the language server walk about 80 ms. The gain is smaller
  than the risk of a stale cache.

## 2.1.1

**From a full review — ask one level up and the key showed, and webhook URLs went out as they were**

After 2.1.0 the whole feature set was reviewed again in seven areas (new features, agent core,
backends, safety, tools, screens, design), and what 2.1.0 changed was shown once more to a
different model (Gemini). Every finding was settled by running it before anything was fixed.
There are no new features.

| | What |
|---|---|
| **Asking one level up showed the key** | Stopping one field short, as in `deel config explain profiles.work`, drew the whole profile as JSON, with its `apiKey` and certificate `passphrase` in plain text on screen and in `--json`. Objects and arrays are now masked all the way down, and `user:password@` in proxy and other URLs is masked the way doctor does it |
| **Webhook URLs went out as they were** | Slack, Discord and Teams webhooks and Sentry DSNs are keys by themselves, but neither the name (`SLACK_WEBHOOK_URL`) nor the shape of the value said so, so they passed both the shell-environment filter and output masking. One `env` from the model was enough to send them into the conversation. They are now recognised by **the shape of the value** and stopped in both places, from one shared set of patterns |
| **A way past strict for Jobs stop** | Whether a Jobs call stops something was read from the `stop` field only, so `kill` or `끝내기`, which the Jobs tool accepts, stopped a server without asking even in strict. It is now judged the way the tool reads it, which also removes a needless prompt for `stop:"false"` |
| **Def and Refs on EUC-KR sources** | Read and Edit recognise legacy encodings, but Def and Refs read raw UTF-8, so a Korean name was "not on that line" and the language server was shown garbled text |
| **deel eval** | One task throwing (permissions or disk space while copying the answer) killed the whole run and saved nothing — now only that task counts as failed. A partial `--only` run no longer becomes the next full run's "last time", two partial runs with no task in common no longer report "same as last time", `--only task-1` no longer also runs `task-10`, and a results file that cannot be written is reported |

### Fixed

- **Completion-check settings were cut down silently.** `checkTimeout` is capped at 600 seconds and
  `checkRounds` at 10; larger values were reduced without a word, so a slow integration check could
  use up every round on "timed out" with no reason given. The first check now says what was reduced
  and to what (chat, `deel run`, and the editor).
- **A write with the same content** showed only the file name in the approval preview, which reads as
  "something changes". It now says there is no change.
- **The failure tail in `deel run`** cut the last 8 lines before dropping blank ones, so a cause
  followed by several blank lines vanished. It now filters first, like the chat screen.
- **Plugin names starting with a dot** (`.hidden`) installed but never appeared in the list. They now
  install under the folder name; anything installed before this can still be removed by folder name.

## 2.1.0

**Hand it off and it keeps going; make it ask and it shows the diff — and a check decides when it is done**

A review from the people bringing deel into a company raised three points: "Does it show a preview and
have a person confirm before changing anything, by default?", "Verification that leans on static checks
has limits — each task needs a golden set", and "the loop needs more engineering". Measured, all three were
right. 2.1.0 answers them.

### The hand-off mode and the asking mode

The approval modes were already separate — `auto` hands the work off, `strict` asks. But neither kept its
whole promise.

| | What |
|---|---|
| **Where auto stood still** | It never asked about tools, but when the model asked a question (Ask) or answered "design it and build it" with a plan first, it waited for a person **indefinitely**. For someone who handed the work off and walked away, that is the same as stopping. In auto it now carries on by itself after 60 seconds with no answer — the question becomes "use your own judgement", and the plan goes ahead. The wait is `askWait` in the config (`0` means never ask). `confirm` and `strict` still wait with no limit |
| **strict asks about every tool that changes things** | It used to ask only about Write, Edit and Bash. The list of changing tools had six entries, but the approval gate was still on the old list. It now also asks about Append, Move, stopping a background command (Jobs stop) and any attached MCP tool. **Reading** output with Jobs does not ask — asking on every read teaches people to just type y |
| **Nowhere to ask means no** | When approval was needed and the caller had nowhere to ask (no confirm), it used to **run anyway**. "Asks" meant "asks if it can". It now refuses and tells the model to find a way that needs no approval |
| **Shows the diff first** | Before asking about Write, Append or Edit, the terminal draws the lines that will change in each file, and the editor (ACP) gets the diff in the permission request. The preview is built with the same logic as the real write (line endings, re-indenting, multi-edit), so what you approve is what gets written |
| **What the preview will not open** | deel's own config and keys, an Edit to a file the model has not read yet, anything outside the working folder, files over 2 million characters (if any one of several files is, the whole preview), document files (Excel, Word, PDF, designs), and writes that would put a masked secret back, which the real tool refuses, are left out. If the preview read a place the real tool refuses, a read would happen even though the tool never ran. Those calls ask in one line, as before |
| **Approval floor in the managed policy** | Put `"approval": "strict"` in the managed policy file (`policy.json`) and that machine cannot go looser. `/mode`, Shift+Tab, `deel run --yes`, `allow` in the config and the editor's "always allow" all stop at the floor, and the screen says why. An unknown value (a typo), or a policy file that cannot be read, counts as strict. `deel doctor` shows it in one line |

The floor only tightens. With `confirm` in the policy you can still go up to `strict`; only going down to
`auto` is refused. A machine with no policy file stays on the default, `auto`.

### A check decides "done" — the completion check

A turn ended at one place: **a step where the model called no tool and only talked**. "Fixed it" was
enough. The means to check existed (Verify, finding the project's check commands, the evidence report), but
all three only suggested or showed, and nothing stopped a turn from ending without running anything.

| | What |
|---|---|
| **`check`** | Put `"check": "npm test"` in the config or pass `deel run --check`, and when the model has changed something and tries to finish, deel runs that command **itself** |
| **A failure goes back to be fixed** | The **end** of the failure output (where it says what went wrong) goes back to the model to keep fixing, together with "do not pass it by editing or deleting the check". 3 rounds by default (`checkRounds`) |
| **Still failing ends as failed** | If it is still red after all its rounds, the turn ends as failed. `deel run` exits with the new code **8**, and `--json` gets a `check` field |
| **The same gates** | The check goes through the same gates as the model's own commands — deny rules, hooks, approval (`strict` asks), the dangerous-command guard. Skipping them because it is in the config would let one line of repository config punch through strict. If it could not run, it is not counted as a pass; it says it could not run |
| **When it does not run** | A turn that changed nothing, a turn that tries to finish after a failure without changing anything, and subtasks. It **never guesses** a command — with nothing configured, behaviour is exactly as before |

### How much it gets done — golden set (`deel eval`)

The 14,000-odd checks measure, against a fake gateway, whether the tools keep their promises. "How many
real tasks does this company's model get done with deel" had never been measured. When switching models or
upgrading deel, there was no number to say whether things got better or worse.

| | What |
|---|---|
| **One task = one folder** | `task.json` (prompt, grading command) · `start/` (starting files) · `golden/` (grading files) |
| **The model never sees the answer** | Each task gets a temp folder with `start/` in it; `deel run` works there, and **only then** is `golden/` added and graded. It is not there while the model works, so there is no way to write to the check |
| **Five examples** | `deel eval --init` — fix a bug · add a feature · rename across files · fix a red test (goes through the completion check) · keep CRLF line endings. Add your own tasks next to them |
| **Repeat and compare** | `--repeat` runs each task several times so you read a rate. Results stay in `golden/.results/`, and tasks that got **worse** since last time are pointed out. Any failure exits with 1 |
| **Nothing is dropped** | A malformed `task.json`, or a folder with `start/` or `golden/` but no `task.json`, counts as a failure — once per `--repeat`. Dropping it quietly would run nineteen of twenty and call it "all passed" |
