## 1.20.0

**A key not written in capitals was going out as it was**

1.19.5 wrote down that this would be measured and shipped on its own. It was
measured. Here it is.

### Only `.env` uses capitals

Secret names were read **in capitals only**. That is the convention in `.env`, so
it sufficed there. Code and JSON/YAML config are not that.

```
API_KEY=sk-real-key-1234       masked
apiKey: 'sk-real-key-1234'     untouched ← went out in plaintext
api_key: "prod.auth.secret"    untouched
accessToken: 'ya29.abcdefgh'   untouched
```

Those middle three are the most common shapes in a config file.

### Only names with a break between the words

camelCase (`apiKey`) and underscore (`api_key`) names count too — but the words
must be **broken apart**: `_key` or `Key`. Accept a plain lowercase `key` ending
and this is what you catch:

```
monkey: 'brown-monkey'      not masked ✓
hotkey: 'ctrl+shift+s'      not masked ✓
turkey: 'roasted12'         not masked ✓
```

**It was measured before it was widened.** Run over the 348 files in this repo, 21
lines are newly masked, and every one of them is a real key (`apiKey: 'sk-…'`).
No line was masked that should not have been.

There is a cost. A camelCase name that is not a secret — `cacheKey`, `rowKey` —
with a quoted value gets masked too; the name alone does not separate `cacheKey`
from `apiKey`. A mangled line is less bad than a secret going out. It is pinned in
a check.

### An identifier is not only Latin letters

When deciding whether a dotted value is a name the code points at, only Latin
letters counted as an identifier. This repo's house style is Korean identifiers,
so **it mangled its own code first.**

```
const API_KEY = 설정.비밀번호;      masked    ← this is code
const API_KEY = config.apiKey;     untouched
```

It now goes by character class. A `#` after a dot counts as part of the
identifier — `obj.#hidden` is JavaScript.

### A `#` inside quotes is not a comment

1.19.4 added "cut the trailing `#` comment before looking". Done as a single
pattern, that forces a choice between two failures. The 16th review found both.

```
API_KEY=prod.v1.secret#(prod)               require a space and this leaks
msg = "a # b"; x.API_KEY = config.apiKey;   don't, and the trailing ; is cut off
```

It now walks the line counting quotes. The first `#` **outside quotes** starts the
comment. Both are right.

### Text that uses only `\r`

Looking for line breaks with `\n` alone makes a CR-only file one single line, and
one `;` somewhere far below then flips that line to "code". Line ends are read as
`[\r\n]`.

### What was not taken

The 16th review raised seven; four were taken. The other three were measured and
declined.

- **`// API_KEY=prod.v1.secret` leaks** — true. But this repo pins that
  **`// API_KEY: config.api_key` must be left alone.** Whether a line inside a
  comment is a secret or is code does not separate on the characters.
- **Everything leaks in a single-line file** — that single line really is code.
  Reading it all as code is correct.
- **Put `\r?$` in the pattern itself** — the line is already split on `\r` where
  it is cut. Writing the same thing in two places is more dangerous when only one
  of them gets fixed.
