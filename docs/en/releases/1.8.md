## 1.8.0

**A full day's work against a corporate gateway that hands out one-hour tokens**

Through 1.7 you could only write a key down. Corporate gateways do not hand out a fixed
key — they hand out a one-hour token, and only after a corporate login. In practice that
meant:

```
morning   copy a token from the portal → paste into deel setup
lunch     HTTP 401
after     go get another one → same screen an hour later
```

The 401 is the worst part. **It does not distinguish "wrong key" from "old key."** People
read that screen and go re-issue a key that was never the problem.

| | 1.7.0 | 1.8.0 |
|---|---|---|
| One-hour tokens | re-paste on every expiry | fetched right before each request |
| On a 401 | plain failure | fetch a new key, retry **once** |
| Starting clean | reinstall | `deel reset` |
| An English screen | 62 lines came out in Korean | 0 |

### Fetching the key instead of storing it

Write down *how to get a key* instead of the key.

```json
"열쇠받기": {
  "명령": "az account get-access-token --resource api://ai-gw --query accessToken -o tsv",
  "수명": 3600
}
```

(The keys are Korean because the codebase is: `열쇠받기` is "fetch the key", `명령` is
"command", `수명` is "lifetime in seconds".)

The command prints a bare token or `{"token": …, "expires_at": …, "headers": {…}}`. A new
one is fetched a minute before expiry — a token that was alive when the request left and
dead when it arrived is exactly the 401 above.

The rules it holds to:

| | |
|---|---|
| You write the path | Nothing is auto-detected. Looking for `az` on PATH would mean you no longer know when this program runs what |
| Separate process | Never `import`ed — code inside our process would see other keys and the whole conversation |
| Asked once per session | Three prompts and people just press the key. A command from admin policy is not asked about |
| Not while sealed | Going out to a corporate login from an `--offline` session would break the promise that lock makes |
| Never written to disk | The token lives in memory for the life of the session |
| Masked | The token, headers that came with it, and anything the command printed to stderr |

**Output with a banner is rejected.** Corporate login tools print `Logged in as …` and then
the token. Sending that whole gets a 400, which on screen is indistinguishable from a wrong
key. The first line is shown back to you, so you know to add `--query`.

`/status` shows `Key store  fetched · 52 min left`. It does not say "stored", because we are
not holding it.

See [Configuration · fetching the key](../config.md) for the details.

### `deel reset` — stop reinstalling to start clean

Wipes settings, memory, sessions, learned facts and plugins, by category.

```bash
deel reset               # shows what exists; changes nothing
deel reset model         # connection settings only
deel reset memory        # memory and pins
deel reset all           # everything (undo history and the audit log survive)
deel reset all --hard    # those too
```

A bare `deel reset` deletes nothing. The default behaviour of a delete command must not be
to delete.

`.deel/mcp.json`, `.deelignore` and `DEEL.md` are **never touched by any category**. A
person wrote those by hand; deleting them is not a favour.

On macOS the key in the keychain goes too. On Windows it lives inside the config file and
goes with it. A key added on a different machine is reported as un-deletable rather than
silently skipped.

### 62 lines of Korean on an English screen

`/lang` reported 100% for English. Starting deel in English and reading the screen turned up
62 lines that were still Korean.

```
/help 명령 목록   ESC 중단   Ctrl+C 중단·끝내기
첫 판단·medium 생각 중…
└ 1개 파일 · 1건 · rg      └ 5줄      └ 1군데 +1 −1
```

Both were true. Every key *in the table* was covered, and those lines had never entered the
table. The thing doing the counting was not counting what people see — and never could,
since you cannot count a key that does not exist.

So there is now a test that **starts deel and reads the screen**. Seven screens in English;
one Korean character fails it. Scanning the source could not have caught this: a line like
`└ 1개 파일 · 1건 · rg` is assembled from fragments and appears nowhere in the source as a
whole string.

It also fails on `1 files` and on a stray `·` doubled or left at the end of a line. Neither
leaves any Korean behind, and both read as carelessly as an untranslated line.

The 21 lines in `/tools` came from one place. The English tool-description table already
existed — it was only swapped in for **what the model is told**, while the screen printed
the original. What you instruct and what you read are separate axes; instructing in English
and reading in Korean is a combination people actually use.

One thing surfaced alongside: the API-spec name differed between screens. The startup header
said "Ollama 규격", `/status` said "Ollama 자체 규격". Both were true, so nobody fixed it.
They now come from one place.

### The corporate gateway that rejected the very first message

Tool argument names had Korean in them. Bedrock validates argument names against
`^[a-zA-Z0-9_.-]{1,64}$` and rejects the whole request if one fails — and it reports only
the **first** offender, so you fix one and the next appears.

They are all ASCII now, with the old names still accepted. And there is a test for it: that
names are shaped the way servers accept, that `required` points at arguments that exist, and
that the docs and the screen use the same names. It caught a real bug the moment it was
written — `Task`'s `required` named an argument that did not exist.

### The front page is English now

`README.md` — the page GitHub and npm open first — is English. Korean is one click away at
[README.ko.md](../../../README.ko.md).

Terminal images are not hand-drawn. `tools/shot.mjs` starts a real `deel` and freezes the
output to SVG. A hand-written screen does not change when the screen does, and ours had
already drifted.
