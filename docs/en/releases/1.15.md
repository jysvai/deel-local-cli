## 1.15.0

**Stop doing the same thing twice**

No new features. Nine places were fixed, and every one of them was **quietly
expensive** — no error, nothing on screen, visible only as money and waiting.

There is a reason that cost is invisible. Most of what this tool pays a gateway
is discounted by the **prefix cache**: if the front of the conversation is
byte-identical to last time, that part bills at about a tenth of list price. So
changing one character at the front does not cost you "one character" — it costs
you **everything after it**. And nothing anywhere says so.

Five of the nine below were exactly that shape.

---

### 1. Switching branches made "you already saw that" talk about a different branch

`/branch` gives each branch its own `messages`. The **file memory** — the table
recording "this file is already in the conversation" — was one per session.

That table is what lets a re-read answer with a one-line "unchanged since you
read it" instead of the whole file again. It is correct only because the
conversation is still holding that text.

Switching branches breaks that.

```
on main      Read(design.md)      13,000 characters enter the main conversation
/branch      switch to a branch   ← the branch's conversation is empty
on branch    Read(design.md)      "unchanged since you read it"
```

The text is nowhere in the branch's conversation. Reading again returns the same
note, because the file still hasn't changed. On the third try the turn dies as a
loop.

The memory and `filesRead` now live on the branch. Forking **copies** it — shared,
a re-read on the fork would change what main gets told, even though main is still
carrying v1 (`test/threads.test.js`).

### 2. `/model` did not carry `열쇠받기` or `vision` across

1.14.0 lined up three doors (chat screen, batch, editor) so they hand out the
same connection object. There was a **fourth**: the `/model` command, which
rebuilds that object when you switch profiles. It was missing `열쇠받기` (fetch
the token by running a command) and `vision`.

So on a corporate gateway with one-hour tokens, typing `/model` once means the
token is never refreshed again. You get a 401 an hour later, and the cause is
the `/model` you typed an hour ago.

There was something worse in the same place. `authcmd.js` holds the fetched
token in **one module-level global** with no record of which profile it came
from. Switching from one corporate profile to another meant **the old company's
token went out on the new endpoint's first request.** It is now dropped on
switch.

The door check went from three doors to **four** (`test/doorparity.test.js`).

### 3. Write read the file twice

Before overwriting, Write reads the old content so it can show what changed. But
it did not use that read for the encoding — it consulted the cache (`ctx.enc`)
and, when the cache was empty, **assumed UTF-8**.

So a CP949 document edited by Write without a prior Read was silently converted
to UTF-8. The screen says `overwrote: memo.txt (4 lines)` — the encoding note is
printed only "when the original isn't utf-8", and the original was already wrong,
so not one character of warning appears. Korean turns to mojibake in the
in-house viewer, the `.bat` stops running, and the user only ever asked for a
one-line edit.

One read now supplies both the text and the encoding. It also halves the reads.

### 4. Only the undo history was left unlocked

`.deel/history/edits.jsonl` holds the **verbatim** contents of files as they were
before an edit. It has to, or undo has nothing to restore. So `.env`, `id_rsa`,
`.npmrc` and kubeconfig land in it in plaintext. They are not masked either —
masking would mean restoring a masked value over the user's real key.

With umask 022 on Linux and macOS that file was created 0644. Any other account
on the machine, any daemon, anyone on a shared home (NFS) could read **the
original contents of every file deel touched** — including files their owner had
deliberately chmodded to 0600. Every other record under `.deel` (sessions,
audit) is locked; this one wasn't.

1.14.0 widened the hole by snapshotting shell writes (`sed -i`, `echo >`, `tee`)
too, so more files land here now. The fix ships alongside.

Directory 0700, file 0600. On Windows `chmod` does nothing, and there the result
is **recorded as not locked** rather than pretending otherwise.

### 5. "Folding happens in batches" was folding one per step

Folding replaces old tool results with a one-line marker when context fills. The
function's own header says: "breaking the prefix to save one line means the whole
conversation goes out again on that step; batching them up is noticeably
cheaper."

But the only gate was a **token threshold** (2,000). A single ordinary Read
result is 3,000 tokens. So past 55% it really did fold one per step — the exact
shape the header claimed had been fixed.

The arithmetic: to save 3,000 tokens on one step, everything after the fold point
(~12,000 tokens) is re-sent at **list price** instead of cache-read (0.1×). Every
step.

**The count is now a gate too.** The most recent four are kept regardless, so
folding waits until four newly-displaced results have accumulated and folds them
together.

```
              results folded per fold
  before      2.8
  after       6.2      ← the prefix is broken less than half as often
```

### 6. The grade flipped mid-turn and shattered the prefix

The model grade (small/medium/large) goes into the **very front** of the system
prompt as one line. And it was graded off a live counter — one truncated
argument, one missed edit, and the value flips.

Which means one line at the front of the prompt changed **between steps of a
single turn**. That is the one place that should be most stable, since a
conversation only grows at the tail. Everything after it — tool definitions,
system prompt, the whole conversation — falls out of cache. Locally, that step
re-runs prefill from scratch. Nothing on screen says why it suddenly got slower.

```
  step 3   frozen part 2,027 chars   grade medium
  step 6   frozen part 2,120 chars   grade small   ← cache is gone from here
```

**It is now graded once per turn.** Nothing learned is thrown away — its
application is deferred to the next turn. `/grade` and `/model` re-grade
immediately, because there the user knows the prompt is changing
(`test/cache.test.js`).

### 7. Every editor tab spawned another copy of the MCP servers

In an editor, `session/new` is **one tab**. People open a project and keep three
or four tabs on it — that is what an editor is for.

Each tab re-read `.deel/mcp.json` and launched the servers listed there again.
Same folder, same config, three tabs, three sets of processes. MCP servers are
someone else's programs, so we do not know what they load on startup — some pull
a whole index into memory, some connect to something remote every time. Opening a
tab also costs one attach per server (two round trips each) with the tab frozen
meanwhile.

**One set per folder.** Different folders still get their own — the tools of the
project next door must not leak in.

```
  3 tabs · 3 processes   →   3 tabs · 1 process
```

One more fix in the same place: **the ACP door never mentioned MCP servers that
failed to attach.** The chat screen prints "couldn't attach MCP <name> — why";
inside an editor the tools were simply absent, with no record anywhere of why.
The user concludes the model got lazy.

### 8. Appending cost scaled with the size of the file

`Append`'s own description says "better to split it up and be sure than to lose
it to truncation". Follow that advice and one file gets twenty Append calls.

All twenty read the whole file. **Three times each.**

| Where | Read | Actually needed |
|---|---|---|
| `바이너리인가` | whole file | first 8,000 bytes (what `looksBinary` looks at) |
| `재는인코딩` | whole file | once (remember it afterwards) |
| `줄수` | whole file + decode + split | add the appended lines to the previous count |

Adding five lines to a 30MB log read 450MB. To write five lines.

```
  5 appends to a 30MB file
  before   736ms   (the same work on a small file: 23ms — 32×)
  after     14ms   (small file 16ms — 0.9×)
```

Whether the remembered line count is still true is decided by **byte size**. If
someone rewrote the file in an editor the size won't match and it recounts
without argument — a correct number slowly beats a wrong number quickly.

### 9. There was a line watching for "stop", and it could not see anything

The directory walk (`walk`) has had a `signal.aborted` check in it for a long
time. But the walk was **synchronous**.

While a synchronous loop runs, the event loop does not advance a single tick —
and the thing that sets that flag is a callback on the event loop. So the check
could only ever see a flag that was **already set before the call**. It could
never change mid-walk.

Which meant "press, then ask" stopped and "ask, then press" did not. The second
is what people actually do. It looked like a guard and guarded nothing.
Keystrokes were not being delivered during that time either — a 20,000-file walk
is several seconds on a corporate network drive.

It now breathes once every 200 files. On that breath the event loop turns over,
and only then does a key get delivered and the flag change.

```
  ESC during a walk of a 3,000-file tree
  before   stops after walking all 3,000
  after    stops at 140
```

Walking itself costs the same — 5,000 files in 107ms (25 breaths), matching the
figure before the change.

### Also

- Three more mutants in `npm run mutate` — the grade latch, the append line
  memory, and the walk's breath. All three are lines that go quietly expensive
  when removed, which is exactly the kind someone deletes in passing if nothing
  is watching. Ten now.

  too. Nothing visible from outside changed.
