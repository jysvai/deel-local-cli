## 2.2.0

**Read-ahead while you type — local models answer the moment you press Enter**

On a local model the wait before the first word was usually **reading**, not thinking. The first call
was what made the server load the model, and then it read the system prompt, the tool schemas and the
conversation from scratch. Both now happen **before** you press Enter, because almost all of the request
is already known.

| What | Before | After |
|---|---|---|
| The first message after starting | The server loaded the model from disk only when the first call arrived (seconds for 7B, tens of seconds for 30B), while the screen just said "thinking" | The model loads the moment the input box appears, with the `num_ctx` it will actually use, so it never loads short and reloads on the first message |
| Pausing while you type (0.4 s) | Nothing happened | deel sends **the same body as the real request**, with what you have typed so far and the answer capped at one token. The server's prefix cache computes that prefix |
| Enter | The system prompt, tools, conversation and your message were read from scratch — tens of seconds on a CPU or a small GPU | The real request picks up what was already read and reads **only the last few characters**. If a read-ahead is still running, the first call waits for it (up to 30 s — past that it is cut off). Otherwise the server would read the same prefix again in a second slot |
| Where it turns on | — | By itself for an address on this PC or the LAN, a model with no price, and not an Ollama cloud model (`…-cloud`). A proxy on 127.0.0.1 forwarding to a paid model is caught by the price table. Never in pipes, `deel run` or editors (ACP) |
| Off and on | — | `DEEL_WARMUP=0` · config `"warmup": false` turns it off; `DEEL_WARMUP=1` · `"warmup": true` turns it on for outside addresses too. A server that refuses it twice in a row turns it off for that connection |
| What you see | — | Next to the model in the status bar, `↯ reading` → `↯ ready`. The `read-ahead` line of `/status` says whether it is on, why, how many were sent, tokens the server read and how long the last one took |

It does not draft the answer while you type. That answer would be thrown away with every key, it would
hold the GPU the reading needs, and an answer here is tool calls — files cannot be edited before you
finish the sentence. Reading wastes nothing: what you typed first stays reused.

If the body sent ahead differs from the first real request by a single character, the cache breaks
there — and that is not an error, so nothing reports it. So both are built **by the same code** (the
tool list and the first-step effort are taken out of the loop and shared, down to the work mode your
words would route to), and the real loop is run against fake Ollama and OpenAI-compatible servers to
compare the two bodies byte for byte (`test/warm.test.js`). A real-terminal test checks that typing and
pausing sends one (`test/pty.test.js`, macOS · Linux).
