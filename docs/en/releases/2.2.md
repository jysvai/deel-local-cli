# Release notes · 2.2.x

What changed in the 2.2 line, and why

Other lines: [2.1.x](2.1.md) · [2.0.x](2.0.md) · [1.x archive](1.x.md) — 1.2.0 through 1.20.13, one line each

## 2.2.4

**The terminal now takes work off the local model**

Reports said the context filled quickly and local models ran slower than the web chat. Work the terminal can do itself moved out of the model.

| Where | Before | Now |
|---|---|---|
| Local auto compaction | The model wrote the summary, up to about 4 minutes at 5 t/s | The terminal records requests, edited files, commands and errors. No model call |
| Conversation kept after compaction | Up to 25% of the window | Up to 8%, in one large cut |
| Folded originals | Gone from the context | Stored with brotli in `.deel/sessions/archive` for 14 days and restored byte for byte with `Recall` `id` |
| Instructions to local models | Followed the UI language | Sent in English, answered in the UI language. The fixed prompt goes from 3,667 to 2,565 tokens on the Qwen3 tokenizer. Change it with `/lang` or `DEEL_PROMPT_LANG` |
| Command output (local) | Cut from the front | ANSI, progress, repeated lines and long runs of passing lines are dropped, then the first 30% and last 70% are kept. Error lines are never dropped |
| Tool calls (local) | Left to the server | `parallel_tool_calls` is on. Servers that refuse it are learned |
| Qwen3 with thinking off | Ran on the server's thinking values (temperature 1.0) | Sends the no-thinking values (0.7, top_p 0.8) |
| Speed figure | Timed by the terminal | Uses llama-server `timings`, the same number as the web UI. `/cost` shows cache reuse and draft hits |
| Self-learning | Commands and model habits | Also records often-edited files to cut search steps next session |
| Screen (local) | Redrawn every 90ms | Redrawn every 250ms |

Typed `/compact` and compaction on remote connections still use the model. A release now runs the full tests once instead of twice.

**Still open:** this has not been measured on a real llama-server on the Mac. Tests use a fake server, and token counts come from the Qwen3-8B tokenizer.

## 2.2.3

**Local models no longer compact until they are full**

Reports said the window still filled up after repeated summaries, and that local models ran far slower than in a web chat.

| Part | Before | Now |
|---|---|---|
| What a summary keeps | Chosen by message **count**, so large tool results could leave the window above 80% after summarizing | Measured in tokens, tool-call arguments included. The tail keeps at most 25% of the window |
| When a summary cannot make room | Shrinking by 1% counted as success, and every step summarized again | Above 70% after a summary, the conversation is cleared on the spot and the turn carries on. No second summary within two steps |
| When summaries pile up | Summaries stacked on summaries | Cleared when the window fills again after two summaries |
| How often clearing can run | Once per turn | Limited by spacing. A long turn can clear again; a refusal right after clearing still ends in an error |
| What clearing carries over | The request, remaining to-dos, touched files | Those plus the latest summary |
| Thinking on local models | `/think off` sent nothing to OpenAI-style servers, so they kept thinking by their own default | Off unless you set it. Sends `chat_template_kwargs: {"enable_thinking": false}`; `/think medium` turns it back on |
| Fixed prompt on local models | A large window got the same long form as the cloud | The short form whatever the window. Empty folder, 65,536 window: 6,676 → 4,282 tokens; the skill list stops at 12 entries of 80 characters |
| Thresholds on local models | Used up to 80% of the window | Summaries start at 40,000 tokens even on a large window, and the gauge marks moved with them |

Summary input now has a cap too (12% local, 50% remote), and local summaries run with thinking off.

**Still open:** this was not measured on the real llama-server on a Mac. The tests use a fake server that imitates a single slot. The `v2.2.2` tag stopped at the pre-publish tests and never reached npm; everything in it is in this release.

618 review-round tags in comments and unused code were removed, and the fix-history paragraphs in the 11 most comment-heavy files were cut down. Those 11 files changed in comments only.

## 2.2.1

**Slow local models no longer re-read the whole prompt at every step**

A report came in: on a 24 GB Mac running a large model from the SSD on llama-server with one slot, calls took very long or failed. That
server pays dearly for reading, since one full read of the prompt takes minutes, and deel kept asking for it.

| Where | Before | Now |
|---|---|---|
| Thinking level | On local models it moved per step (`medium → low → low`), per wording and per mode. With a template that puts the level text at the very start of the system prompt (Qwen3.8), each move re-read everything | It no longer moves by itself. It stays at what `/think` set (or the default) |
| Read-ahead · after a turn | Sent each time the input box appeared, shaking the end of the cache for nothing | Sent only when the box first appears, when the conversation shrank, or when the model changed |
| Read-ahead · Enter | Waited up to 30 s for the one running | Waits up to 3 s, then cuts it off. What was read stays on the server and the real request picks it up |
| Read-ahead · slow server | Sent at every pause | After a typed draft takes over 5 s, no more drafts are sent. `/status` says so |
| Read-ahead · turning off | A 503 while the model loaded, or two reads over 2 minutes, turned it off as "server refused" | Only a real refusal (such as 400) turns it off |
| Timers | Local servers were also cut off at 5 and 10 minutes. `deel setup` checks stopped at 60 s, saving a healthy connection with tools and streaming off | This PC and the LAN wait up to 30 minutes. Outside addresses are unchanged |

**Still there:** a turn that changes the work mode re-reads the conversation part, because the mode text comes before the conversation. On a slow
server with a long conversation, `/work code` pins the mode and that stops.

| Mutants | 2,065 | **2,077** — 12 weak spots in guarding the prefix |

## 2.2.0

**Read-ahead while you type — local models answer the moment you press Enter**

On a local model the wait before the first word was usually **reading**, not thinking. The first call
was what made the server load the model, and then it read the system prompt, the tool schemas and the
conversation from scratch. Both now happen **before** you press Enter, because almost all of the request
is already known.

| What | Before | After |
|---|---|---|
| The first message after starting | The server loaded the model from disk only when the first call arrived (seconds for 7B, tens of seconds for 30B), while the screen just said "thinking" | The model loads the moment the input box appears, with the `num_ctx` it will actually use, so it never loads short and reloads on the first message |
| Pausing while you type (0.4 s) | Nothing happened | deel sends **the same body as the real request**, with what you have typed so far and the answer capped at one token. The server's prefix cache computes that prefix |
| Enter | The system prompt, tools, conversation and your message were read from scratch — tens of seconds on a CPU or a small GPU | The real request picks up what was already read and reads **only the last few characters**. If a read-ahead is still running, the first call waits for it (up to 30 s — past that it is cut off). Otherwise the server would read the same prefix again in a second slot |
| Where it turns on | — | By itself for an address on this PC or the LAN, a model with no price, and not an Ollama cloud model (`…-cloud`). A proxy on 127.0.0.1 forwarding to a paid model is caught by the price table. Never in pipes, `deel run` or editors (ACP) |
| Off and on | — | `DEEL_WARMUP=0` · config `"warmup": false` turns it off; `DEEL_WARMUP=1` · `"warmup": true` turns it on for outside addresses too. A server that refuses it twice in a row turns it off for that connection |
| What you see | — | Next to the model in the status bar, `↯ reading` → `↯ ready`. The `read-ahead` line of `/status` says whether it is on, why, how many were sent, tokens the server read and how long the last one took |

It does not draft the answer while you type. That answer would be thrown away with every key, it would
hold the GPU the reading needs, and an answer here is tool calls — files cannot be edited before you
finish the sentence. Reading wastes nothing: what you typed first stays reused.

If the body sent ahead differs from the first real request by a single character, the cache breaks
there — and that is not an error, so nothing reports it. So both are built **by the same code** (the
tool list and the first-step effort are taken out of the loop and shared, down to the work mode your
words would route to), and the real loop is run against fake Ollama and OpenAI-compatible servers to
compare the two bodies byte for byte (`test/warm.test.js`). A real-terminal test checks that typing and
pausing sends one (`test/pty.test.js`, macOS · Linux).
